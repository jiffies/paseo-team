# 经用户同意的独立审查

仅执行用户选定阶段和冻结名单。任务复杂或风险较高可以成为建议审查的理由，不能自动启用。主控不计入审查人数；人数只表示每个所选阶段的成员数，方案与最终交付必须是不同新会话。

## 派发与独立性

两位方案成员可复用本机官方 `paseo-committee`，前提是能严格使用已选 Profiles；官方两人流程不等于支持任意人数。三人或更多方案成员使用独立 `paseo-advisor` 会话，由主控按下面的独立首轮、交叉质疑和证据裁决流程主持。交付阶段始终每位成员各开一个新 Advisor。

先派出同一阶段的全部成员，再等待完成通知。首轮给相同的原始业务需求、客观事实、实际路径、候选版本及证据索引；不透露其他成员意见，不把主控提案写成既定正确答案。交接不带 Skill 调用前缀或已解析的选人参数，明确本会话只执行独立审查，不重新编排团队。无需成员加载整个团队 Skill 或完整选人配置；保留官方只读边界。

最终 Reviewer 不复用本次方案成员、Developer 或动态验证者的会话。修复复审则复用本阶段各自 Reviewer 会话。成员可与开发者使用同一个 Profile，但不能是同一个会话；不同 Profile 也不一定代表不同模型。没有可用成员时报告缺口，不擅自替换或凑人数。

## 方案审查提示

给每位成员相同的核心目标，再加具体任务材料：

> 你是独立方案审查者。你的任务是检验问题定义和候选方案是否成立，包括挑战主持者的提案；不是替既定方案背书。请从原始目标与实际代码出发，列出关键假设及证据，寻找更简单的备选、能推翻方案的反例和失效条件。区分用户必需要求与建议增强。结论可以是原方案合理，也可以要求修改或因证据不足阻断，不必为了对抗而制造反对意见。请指明决定方案所缺的最小验证。

在大量实现前完成已选方案审查。首轮后只交换实质分歧，重点检验决定性前提，而非长篇重复彼此报告。需要运行事实时由单 Developer 做实验，不让只读成员运行会写文件的测试。

最多两轮实质论据交换仍有关键未知时，补最小证据或报告 `BLOCKED`，不能以投票或一致措辞代替事实。主控记录方案 P、必需 AC、关键假设与取舍；所有方案成员明确接受同一 P/AC，且无未解决阻断后才开始正式实现。根本假设或重要契约改变时，在已授权的方案审查范围内重新确认。

## 交付审查提示

每位 Reviewer 收到同一 task_id、原始目标、P/AC（如有）、M/C、真实源码位置、证据索引、已知失败及未验证项。从索引按需读取验证命令与原始结果，不把长日志和整份开发者对话复制进提示。附以下目标：

> 你是独立交付审查者。请尝试证伪“本次原始任务已经完成，当前证据足以支持交付”这一主张。不要仅复述作者或主控总结，也不要只看 diff。逐项核对用户要求 → 实际实现 → 真实调用路径 → 可观察行为 → 验证证据，主动找漏做的要求、未接入的逻辑、边界反例，以及测试通过仍不足以证明目标的情况。作者、其他审查者和主持者的结论都可被质疑。每个阻断需给出对应需求、实际位置或证据、影响和最小验证办法。区分已证实问题、合理推断、证据不足与可选改进；不可把建议增强升级为原始验收要求。只批准你实际检查的候选和阶段，不将局部批准扩大为整体上线或真实交易成功。

成员可以按 Profile notes 有不同侧重，但全部承担完整任务验收责任，不固定“Claude 看设计、Codex 看测试”。特别核对：

- 原始需求中未出现在 diff 的部分，以及真实入口、配置与依赖是否接通。
- 测试断言是否测到了目标；mock 成功、进程启动、请求尝试不自动等于真实结果。
- 运行证据是否对应当前 C、环境及所声称的边界；区分从代码推断和实际复现。
- 限额、单位、时间窗口等决定性计算是否成立；不因对方是 Reviewer 就接受计算结果。
- 主控的最终综合说明有无超出证据的新保证；仅批准某阶段时明确剩余任务。

静态分析不能决定的，提出可执行的验证请求交 Developer。已同意审查且确需独立动态证据时才另开有能力的验证会话，在固定候选隔离环境运行，不改正式候选。Advisor 保持只读。

优先按索引检查当前候选的关键证据。官方活动能够补足点击方式、实际命令等缺口时，读取对应片段；只有无法定位或结果缺失时才扩大读取。版本与哈希核对可批量执行并只回报差异，不能因此省掉各自对源码、调用路径和验证有效性的独立判断。

## 成员之间如何对抗

首轮全部完成后，主控整理短争议表：主张、提出者、证据位置、可能反例、缺口。将实质争议同时发给该阶段全体成员：

> 独立核对这些主张及证据，不按身份、人数或措辞强弱判断。请指出哪些质疑成立、哪些已被证据推翻、哪些仍缺决定性验证；需要改判时明确撤回原结论。你的任务不是坚持上一轮意见，也不是与多数人一致。对主持者新增的交付保证同样检查。

有分歧才交叉质疑，不机械制造多轮辩论；一致且证据充分可停止。三人审查不是两人拉票：有依据的阻断必须解决，不能按多数票忽略、移除提异议者或临时降低人数。额外建议不应阻碍符合原始要求的交付；事实错误的阻断可由证据推翻，并由相关成员更新结论。

## 修复与放行

每位短回报包含身份、阶段、P/AC 或 M/C、实际检查范围、证据对应、阻断和未验证项，以及结论：

- `APPROVE`：本阶段必需行为有足够证据，无未解决阻断。
- `REQUEST_CHANGES`：写明位置、影响、对应要求及验证办法。
- `BLOCKED`：缺决定性证据或无法检查候选。

无阻断时简短给出结论、检查范围和关键证据入口，不逐项复述所有成功检查。存在问题时展开对应需求、影响和最小验证；不要为缩短报告删掉未知。首次回报前核实文件行号和证据引用，避免把内容偏移当成行号；发现引用错误应更正，并说明是否影响结论，无需为单纯勘误重跑未受影响的检查。

只有 Developer 修改正式候选。关键缺陷尽可能证明新检查在旧行为失败、新行为通过，再执行必要回归；不为小改动盲目重搭全仓验证。

C、M 或实质 P/AC 改变后旧批准失效。全体所选成员重新确认新版本，可以只审差异、影响和新增证据并引用未变范围，不必重写首轮报告。仅选择交付审查时不能自动追加方案委员会。通知截断或缺版本时补读原报告，不能凭完成状态放行。

放行条件：本阶段必需目标有证据、必要检查通过、关键未知和阻断为零、冻结名单全体批准同一版本且版本不再改变。最多三轮实质修复仍未满足时报告缺口，不无目的争论；预算耗尽、主控单方声明或 main 前进都不算通过。
