# 经用户同意的独立审查

仅在用户明确要求或同意相应审查时读取并执行。任务复杂或风险较高可以成为提问理由，不能作为自动启用本流程的授权。完整对抗性模式包含复杂方案委员会与交付双审；用户只要求其中一项时只执行该项，不覆盖“不要 review”。

## 方案委员会

在冻结复杂方案和大量实现之前使用本机官方 `paseo-committee`，复用 Architect/Claude 与 QA/Codex，分别创建全新会话。双方先收到相同的原始需求、事实、约束和代码路径；已有提案只作为待检验候选。

首轮独立回答：问题是否定义正确，假设有何证据，有哪些更简单的替代，何时失效，还缺什么验证。之后才交换论据，允许推翻主持者或自己的原方案，不强行安排一人赞成、一人反对。

决定性运行事实交 Codex 做实验。最多两轮实质交换仍不收敛时补证据或报告 `BLOCKED`，不能投票消除事实争议。主持者记录方案 P、必需 AC、关键假设和取舍；无未解决阻断后再交接实现。实施发现根本假设失效或重大契约变化，在已获同意的方案审查范围内返回讨论。

## 独立交付双审

使用两份官方 `paseo-advisor`，先派出两份再等待通知。复用 Profiles，不复用本次设计委员会、Developer 或独立动态验证者的会话。首轮互不看对方结论；修复复审继续各自 Reviewer 会话，不重建整套团队。

两位收到同一 task_id、原始目标、P/AC（如有）、M/C、源码路径、验证记录和已知失败。保留官方只读后缀，不将 `/paseo-team` 转发给成员递归执行。

双方都沿下列证据链判断任务完成情况：

**原始需求 → 实际实现 → 真实调用路径 → 可观察行为 → 验证证据**

- 看漏做的需求和未接入的入口，不只读 diff 或作者总结。
- 阅读相关实际源码、边界和错误路径，寻找能推翻结论的反例。
- 阅读测试断言与实际结果，识别 mock、自证预期、跳过或未覆盖的关键路径。
- 核对证据与当前 C 的对应关系，区分已证实问题、被推翻质疑和仍未知事项。

Claude 侧重需求、设计与整体逻辑，Codex 侧重实现、反例和测试证明力；两者仍都承担完整任务验收责任。已有证据可共同读取，首轮判断独立；哈希、版本和检查索引交工具批量核对，不要求两人手工重算所有机械数据。

静态审查不能决定的，明确请求 Developer 补运行验证；关键自报证据不可信时才另派独立 QA/Codex 验证任务。Advisor 本身不运行会写文件的测试，也不充当实现者。

## 结论、修复与复审

每份短回报包含身份、候选、实际检查范围、必要 AC 与证据的对应、问题和未验证项，以及一个结论：

- `APPROVE`：必需行为有足够证据，没有未解决阻断。
- `REQUEST_CHANGES`：写明问题位置、影响与验证方法。
- `BLOCKED`：缺少决定性证据或无法检查候选。

不能把一致意见当作事实证明，不能凭作者自报或 Agent 完成状态批准。通知截断时主控补读完整报告；有依据的阻断不能被主控单方撤销。

只有 Developer 修改正式候选。关键缺陷尽可能证明新检查在旧行为上失败、新行为上通过，然后执行相关回归。不要为微小变更盲目重搭全仓验证；必要的项目检查仍须完成。

C、M 或实质 P/AC 改变后旧批准失效。两位对新版本重新给结论，可以只审差异、影响路径及新增证据，引用已审且未变的范围；不必重写整份首轮报告。方案有根本变化且方案审查已获同意时才回委员会；原先只要求交付双审时，可询问是否补充方案审查，不能自动扩大范围。

双审放行条件是：必需目标有证据，必要检查通过，关键未知和阻断为零，两人批准同一候选且候选不再改变。最多三轮实质修复仍无法满足时报告缺口和下一步，不继续无目的争论，也不把 main 前进算作一次修复失败。
