# 日常任务执行

仅首次派发或恢复缺失的任务上下文时读取。本文件不要求加载 setup 示例；配置缺失、需要保存或修改默认团队时才读 [配置管理](configuration.md)。

## 解析与冻结

通过本机官方 `paseo` 能力取得本次 Profiles/notes，把公开字段 `id/name/provider/model/modeId/thinkingOptionId/featureValues/notes` 保存为 `profiles.json`。主控身份来自可信运行环境，用 `--lead claude`、`--lead codex` 等，不用 Developer 身份猜测。全局配置在同一主机/用户的 `~/.config/paseo-team/config.json`。

选择优先级为：本次参数 → preset → 当前主控默认 → 通用默认；显式 `null` 不回退。工具校验参数、角色与人数，输出本次名单。将目标与参数分开，不把整段用户输入拼成 shell 命令。

```text
node <skill-dir>/scripts/team.mjs resolve --lead codex --profiles <profiles.json> --snapshot <task-dir>/team.json --task-id <id> --repo <repo>
```

可加 `--dev`、`--preset`；`--audit 0/2/3/名单` 同时控制方案和交付，不能与 `--plan`/`--review` 混用。后两者分别控制阶段；任一本次审查参数替换 preset 的整个审查范围。没有审查参数或含审查的 preset，始终不审查；`--audit 0` 明确关闭两阶段。自然语言“审查一下”按交付两人理解，“完整对抗性审查”按两阶段各两人理解，具体要求优先。

`team.json` 放在候选外的稳定任务目录，不覆盖已有快照。冻结前核对所选 Profile 的 notes，缺少 model 时通过官方能力确认实际设置；缺失、不兼容或不可确定时报告，不自行换人、降档或减少人数。未保存配置时工具只在唯一匹配时生成旧 Developer/Codex、QA/Codex、Architect/Claude 的兼容草案，Codex 主控的审查组不自动补 Claude。

按输出的 `provider/model` 和完整设置调用官方 `create_agent`，将 `modeId/thinkingOptionId/featureValues` 映射到其实际 schema，不传不存在的 `profile` 参数。派发后核对返回身份与设置，不符时停止该成员后续工作并说明。任务记录维护 task_id、阶段、Agent ID、P/AC/M/C；快照不代表已执行或已批准。

续聊直接使用任务记录；仅缺少名单时运行 `team.mjs status --snapshot <task-dir>/team.json`。不重新 resolve、setup 或创建同角色会话。用户明确换人时记录新阶段/新快照及批准失效，不覆盖原快照。仅分析任务不调用要求 developer 的解析流程，也不进入实现与合并。

## 探索与交接

主控先核对项目指令、实际路径、Workspace、分支和用户改动，只读足够确定目标与必需验收的材料。已有 worktree 就复用；缺少时用官方能力建立，不要求重建已有隔离或手填 setup scripts。

- **目标明确的小改动**：主控给目标、约束和验收，将代码定位、影响分析、实现细节及验证交给 Developer；不先全面探索再让其重做。
- **陌生或复杂任务**：同一个 Developer 先做有范围的调研，返回关键文件位置、已有机制、证据和需要主控决定的问题。通常只读；必要实验另明确允许的范围。主控按需读取决定性代码并确定方案，再让该 Developer 继续实现，不另起探索者或第二位开发者。若不存在必须等待的决策且已授权实现，可直接继续，不机械增加汇报回合。
- **已选方案审查**：调研不代替独立方案审查；按照 [审查流程](review.md) 完成已授权阶段后再正式实现。必要需求或操作授权仍缺失时，只继续不依赖答复的工作。

通过官方 `paseo-handoff` 给接收者自足简报：原始目标、约束、非目标、必需 AC、实际路径、基线 M、已定方案/未知问题、验证要求及交付终点。去掉 Skill 调用前缀和已解析选人参数；明确“只执行本角色，不重新编排团队”。保留用户语义，不让成员重读配置管理、完整名单和主控探索历史。方案成员、Reviewer 只收本角色必要材料。

派出后返回成员信息，等完成通知，不轮询。Developer 是候选唯一写入者；同一任务的调研、实现、修复复用该会话。主控负责决策，不写业务代码、不运行测试；Reviewer 保持独立只读。只有用户要求独立验证，或已授权审查确需独立动态证据时，才另派隔离验证会话。

## 验证与回报

Developer 运行项目已有格式化、lint、CI 及与需求相符的行为/视觉验证，不为凑检查数量创建工具链。对输出冗长的普通检查，可用 [检查输出工具](checks.md) 保存完整日志并只回传结果；失败、截断或未知不因摘要消失。不要自动包装未知命令或真实凭据验证。

固定候选 C。通常用一份 `delivery.json` 或现成 CI 索引记录 task_id、M/C、cwd、完成行为、命令/退出码、原始证据位置和未验证项，不为每条命令再造报告。受测内容必须对应 C；提交前验证可用源码哈希等证明提交后未变，版本检查批量输出匹配摘要或差异。索引和纯证据放在候选外的稳定任务目录；应交付的测试和文档仍进入候选。截图优先复用文件，避免在对话搬运 Base64。

正常回报通常用数行表达：状态、C、完成的必需行为、检查结果、阻断/未验证项、证据入口。约 1500 字符是通常上限而非目标；不复述全部成功日志、源码和哈希，也不为限字隐去问题。主控直接核对原始目标、版本与结果，不再充当额外全量 Reviewer。通知截断、缺版本或缺依据时，只补取所需的原始活动/日志；不能凭完成通知或摘要放行。

默认交付候选后返回，main 的状态不阻止独立候选交付。准备已授权的本地合并时再读 [Git 工具](tools.md)，由 Developer 在共同锁内检查并只快进到 C；不持锁开发或等待测试。若需独立审查，按已选范围收齐全体对同一版本的批准。

最终说明完成行为、验证、候选、是否审查/合并及剩余未知。只记录可取得的耗时、token/缓存、费用与返工，不另派计费审计 Agent，也不扫描全机日志。优化以同类任务的实际消耗和返工验证，不预先承诺比例。
