# Paseo Team

方案不是主持者说合理就合理，任务不是实现者说完成就完成。对抗性审查检验目标、假设、方案和完成声明；以可检查的事实解决异议，允许证据不足时暂不通过，也允许证据充分后停止争论。不预设谁必须反对，不要求凑缺陷数量。

这是叠加在官方 Paseo Skills 上的工程政策，不是新编排器或程序强制门禁。当前 Claude 就是主持者；不创建接单入口、另一个主控、自定义 provider、角色文件或后台脚本，不 fork 本工作流。用户在不同任务的独立 worktree Workspace 中启动 Claude；成员使用原生会话 Tab。

## 1. 复用能力，划清职责

先按需读取本机已安装的官方 Skill。官方决定工具用法，本 Skill 决定任务分工和放行条件；不复制官方正文、不修改官方文件、不把 `/skill` 当 shell 命令。

| 官方 Skill        | 本工作流用途                                                               |
| ----------------- | -------------------------------------------------------------------------- |
| `paseo`           | 读取 Profiles 与 notes，应用完整运行设置，管理 Workspace、Agent 和完成通知 |
| `paseo-committee` | 两人独立分析复杂方案，再交换论据、解决分歧                                 |
| `paseo-handoff`   | 交接实施子任务，必要时交接独立 Codex 验证任务                              |
| `paseo-advisor`   | 两份独立交付审查；局部疑点的第二意见                                       |
| `paseo-help`      | 工具、配置、运行或回执异常时排障                                           |

先读取实时 Profiles 和 notes，再按官方方法应用配置；不硬编码模型、模式 ID、思考档位或猜测工具参数。同一 Profile 可以创建多个新会话，它不是固定 Worker。

| 职责                       | 现有 Profile         | 边界                                                    |
| -------------------------- | -------------------- | ------------------------------------------------------- |
| 当前主持者                 | `Architect` / Claude | 分析、调度、读取事实、决策与验收；不写代码、不运行测试  |
| 实现与验证                 | `Developer` / Codex  | 正式候选唯一写入者；实现、验证、记录、修复和 Git 写操作 |
| 方案成员或 Claude Reviewer | `Architect` / Claude | 新会话，只分析和审查，不接管任务或再建团队              |
| 对照成员或 Codex Reviewer  | `QA` / Codex         | 新会话，只分析验收、实现、反例及测试证明力              |

名称变化时可依据 notes 和 provider 确认等价配置并说明；缺少匹配配置时报告缺项，不静默创建或替换。官方允许的 provider 发现回退不适用于本工作流的既定角色约束。保留现有 Claude Auto、Codex Full Access 设置，不自行改全局配置。

所有 Claude 都不写业务、测试、配置、脚本，也不运行安装、构建、格式化、服务或浏览器验证。committee/advisor 每次 briefing 保留本机官方要求的禁止编辑后缀，成员不得编辑、创建或删除文件。Full Access 下的只读职责是任务约束，不是沙箱。

动态验证交 Codex：通常由 Developer 执行；关键风险或自报证据不足时，另用 QA Profile 创建独立验证会话，在固定候选的隔离副本执行。该会话是验证任务，不是只读 Advisor，不改正式候选，也不充当两位最终 Reviewer。派单只给本次职责和必要事实，不把整份团队工作流交给成员递归执行。

## 2. 从问题出发审查方案

读取实际项目，记录原始目标、约束、非目标、已有行为和可验证的验收条件 AC。核对 Workspace、工作目录、分支及用户改动；已有任务 worktree 就复用，缺少隔离则通过官方能力建立，不能假称当前主会话已移动。

简单、局部、验收明确的任务可以直接形成短方案，仍须交付双审。以下任一情况必须在方案冻结和大量实现之前调用 `paseo-committee`：

- 架构或跨模块契约变化，多个合理方案需要权衡。
- 根因或关键需求不明、范围较大、反复修复失败。
- 并发、恢复、迁移、权限、资金风险，或缺少证据的关键性能推断。

简短说明复杂度判断，不让用户手动选择模式，也不为跳过审查把复杂任务降为简单任务。

指定 Architect/Claude 与 QA/Codex，两位成员从全新上下文并行分析。双方收到相同的客观事实、原始需求、约束和真实代码路径；已有提案标为待检验候选，已有失败和不利证据一并提供，不让成员替已拍板方案盖章。

首轮双方独立回答：问题是否定义正确；假设有何依据；有哪些可行方案和更简单的替代；各自在什么条件下失效；遗漏什么；还需什么证据。首轮完成后才交换具体论据，允许挑战主持者或推翻自己的判断。

决定性运行事实由 Codex 补实验。最多两轮实质论据交换仍不能解决时，补证据或标为 `BLOCKED`，不靠投票或强行一致收敛。这是本 Skill 对官方讨论流程的轮次与证据约束，“证据不足，暂不能决定”是合法结果。

主持者据此记录方案版本 P、理由、AC、关键假设、风险和验证计划。双方无未解决阻断后才冻结方案；非阻断偏好可由主持者作有依据的取舍。实施发现根本假设失效或需重大契约变更，回到方案评审。

## 3. 交接实施，冻结可检查的候选

通过 `paseo-handoff` 将实施子任务交给 Developer，提供目标、方案 P、AC、路径、约束、当前状态、失败尝试和验证要求。正式候选同一时刻只有一个写入者。

Handoff 创建成员后立即返回 Agent/Workspace 信息，不同步等待、不轮询。当前 Claude 保留主持责任，在之后收到官方完成通知时继续本流程。成员仍处于子代理轨道；是否 detach 由用户操作，不另造独立启动模式。工具发送成功不等于任务执行成功；异常先核对真实状态，不盲目重发。

Developer 必须根据真实项目运行已有格式化、lint、CI 和必要验证，逐项对应 AC，不删除测试、弱化断言、吞异常或改需求来换取通过。验证记录包含：

- 命令、工作目录、候选版本、环境/配置标识和退出码。
- 可直接核对的脱敏原始结果路径、关键断言和覆盖范围。
- 未验证项、失败、跳过项及其原因。

普通检查隔离真实凭据。禁止读取、展示或转发 `.env` 和其他秘密，不输出环境变量全集。仅在任务明确授权真实 API 验证时，允许已检查无泄密日志的可信项目程序通过既有机制内部加载凭据；这不授权 Agent 查看秘密，也不授权交易、部署或远端写入。必要的变量检查只返回指定变量的 configured/missing 状态。

Developer 适配最新本地 `main` 后，固定基线提交 M 和候选提交 C，绑定 P、AC 与 task_id。C 必须包含本任务所有交付文件，包括源码、测试、文档、运行配置和依赖锁；不能遗漏未跟踪实现。保留用户无关改动，不盲目全量暂存。纯验证报告可放在候选外，但必须标注对应 C，且不能因此排除本身属于需求的交付文档。

候选源码工作树和索引须与 C 一致。检查或 hook 改写内容后重新固定 C、补验证；基于相同文件树的提交前结果须有可核对的树身份，否则在 C 上重跑。发出 `READY_FOR_REVIEW` 后冻结候选，不能边审边改。

## 4. 两份独立审查，从原始目标追到行为

分别使用 `paseo-advisor` 创建 Architect/Claude 与 QA/Codex Reviewer。最终 Reviewer 不得复用 Developer、独立动态验证者或本次设计委员会的会话；可以复用 Profile，不复用这些上下文。同一轮修复复审可继续各自 Reviewer 会话。

双审是本 Skill 对单 Advisor 的组合：先准备并派出两份独立 briefing，再等待完成通知并收齐报告，不先执行完第一份再启动第二份。双方收到同一 task_id、原始需求、约束、P、AC、M、C、实际路径、验证记录和已知事实，首轮不看对方结论。不要将 `/paseo-team` 作为转发 Skill 交给 Advisor 再执行。

每位 Reviewer 都独立核对以下完整证据链；作者总结只用于定位：

**用户要求 → 实现位置 → 真实调用路径 → 可观察行为 → 验证证据**

| 待检验主张 | 必须检查                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------- |
| 功能完成   | 从原始目标逐项追踪 AC；检查漏做需求、未接入入口、调用方、配置、依赖及相关未修改代码         |
| 逻辑正确   | 阅读 M→C 完整变更及真实源码，检查契约、边界、错误路径和回归，寻找可验证反例                 |
| 验证有效   | 直接阅读测试和断言，核对实际执行范围与原始结果；识别只测 mock、跳过路径、自证预期或遮蔽错误 |
| 可以交付   | 代码、配置、验证记录和审查均绑定当前 C；检查剩余必需需求、风险与关键未知                    |

Claude 侧重需求、设计和完整逻辑，QA 侧重实现、反例和测试证明力；侧重点不免除任一方的完整任务验收责任。静态推断不能确认运行行为时，提出具体 Codex 验证请求，不私自运行会写文件的测试。

每份报告包含成员身份和会话、task_id、P/AC/M/C、实际检查范围、AC 到实现及证据的对应关系、关键质疑与处置、剩余未知，以及一个结论：

- `APPROVE`：所需证据充分，未发现阻断。
- `REQUEST_CHANGES`：存在有依据的缺陷或缺项，写明位置、影响和验证方法。
- `BLOCKED`：缺少决定性证据、无法读取候选或前提不成立，不能判定通过。

区分已证实、待验证和已被推翻的质疑；无法核验的范围保持未知，不能声称审完全部代码。主持者读取实际成员报告；Developer 可以代存脱敏记录，不能代写他人的结论。

## 5. 修复、复审与放行

先收齐独立报告，再交换实质分歧。主持者不能单方撤销有依据的阻断；Developer 的反驳也须提供可检查的代码、推理或实验。动态事实用实验解决，不能让两位成员互相附和。

只有 Developer 修改正式候选。关键缺陷尽可能补可复验检查，证明旧行为因目标缺陷失败、新行为通过，再运行相关回归；无法复现时说明原因和替代证据，不把构建失败当作缺陷复现，不为此擅自重搭全仓 CI。

新 C、新 M 或实质改变后的 P/AC 均使旧批准失效。双方都须审查更新后的同一版本，可聚焦变化及影响，但不能沿用另一方旧批准。根本方案变化先回委员会。

同时满足以下条件才算通过交付验收：

1. 原始目标和全部必需 AC 均有可核对证据。
2. 必要验证通过，对应当前 C，关键未知为零。
3. 两位独立 Reviewer 对同一 P/AC/M/C 给出 `APPROVE`。
4. 阻断为零，候选未再变化。

非阻断建议可以有依据延期。最多三轮实质修复仍不能满足条件则 `BLOCKED`，说明缺口与下一步；main 前进不算一次代码修复失败。纯分析任务止于方案与证据，不编造实现、测试或合并。用户要求“仅分析”或“等待确认”时以该限制为准。

## 6. 各任务独立合入与结束

每个任务独立 worktree、独立团队，各自适配并合入最新本地 `main`；不使用滞后的 `origin/main` 代替，不新增统一集成任务。后合并者负责解决文本和逻辑冲突，再验证、双审。

Developer 仅复用项目已有的可靠共同锁/合并门禁，且只在最终推进 main 时持锁，不持锁等待测试或审查。锁内核对 main=M、C 包含 M、相关工作树干净且无未完成 Git 操作，然后只快进到已审 C。main 变化就回任务 worktree 更新基线、验证并双审。

没有可靠共同保护时停止自动合并，明确报告“候选已审，尚未合入”，不以提示词冒充并发保护，不擅自新增常驻调度器。不得覆盖、reset 或 stash 用户改动；未经授权不 push、部署、交易、归档或删除 worktree。交付验收通过和本地合并成功分别报告。

同任务可继续已有 Worker；新任务使用新上下文。需要交接长上下文时保留必要事实与证据路径，先停止旧写入者。只在阶段结果、实质阻碍或需要用户决策时更新，不轮询催促成员。

结束时报告：原始目标完成情况、实际检查的行为与证据、关键质疑及处理、两份最终结论和候选 C、未验证项、是否合入本地 main。多 Agent 不保证零缺陷，批准文本不等于程序强制门禁；不编造测试或审查。完成已授权目标后停止。
